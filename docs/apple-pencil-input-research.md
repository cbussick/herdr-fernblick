# Apple Pencil missed-input research

Research snapshot: 2026-10-30. Scope: React Flow playground, perfect-freehand **1.2.3**; primary upstream sources only. The reported iPad Chrome/WebKit screenshot, working finger input, and missed Pencil strokes do **not** establish a hardware defect, browser bug, or speed-dependent cause. No physical-device reproduction was performed; the parent investigation owns state-machine testing.

### perfect-freehand is geometry, not input acquisition

Version-pinned [`getStroke.ts`](https://github.com/steveruizok/perfect-freehand/blob/v1.2.3/packages/perfect-freehand/src/getStroke.ts) only composes `getStrokePoints` and `getStrokeOutlinePoints`, accepting coordinates/options and returning a polygon. It does not install event listeners or capture pointers. The [README](https://github.com/steveruizok/perfect-freehand#example) places `setPointerCapture`, React handlers and `touchAction: 'none'` in **consumer example code**. Upgrading geometry cannot restore a `pointerdown` never delivered to the page. **Confidence: high.**

Pressure is separate from stroke lifecycle. The [Pointer Events specification](https://www.w3.org/TR/pointerevents3/#dom-pointerevent-pressure) defines pressure in `[0,1]`, with `0.5` for unsupported pressure in active-buttons state and `0` otherwise. Do not require `pressure > 0` to recognize contact. Upstream [PR 35](https://github.com/steveruizok/perfect-freehand/pull/35) fixed zero-pressure fallback in 2021; [1.2.3 source](https://github.com/steveruizok/perfect-freehand/blob/v1.2.3/packages/perfect-freehand/src/getStrokePoints.ts) explicitly accepts nonnegative pressure, including zero. The README requires `simulatePressure: false` to use supplied pressure, or `thinning: 0` for constant width. **Confidence: high.**

### Cancellation, palms, and capture

The [specification](https://www.w3.org/TR/pointerevents3/#suppressing-a-pointer-event-stream) permits stream suppression for palm rejection and requires cancellation when browser gestures take over. [`touch-action`](https://www.w3.org/TR/pointerevents3/#the-touch-action-css-property) controls native pan/zoom arbitration; set it before contact, not after gesture recognition. It is **not** a documented universal Scribble opt-out. WebKit's missing gesture-cancellation implementation [193962](https://bugs.webkit.org/show_bug.cgi?id=193962) was fixed in 2019; cancellation itself is expected behavior, not automatically a bug.

[Capture](https://www.w3.org/TR/pointerevents3/#setting-pointer-capture) routes subsequent events for an active pointer; it cannot force native events into existence or prevent all cancellation. [`isPrimary`](https://www.w3.org/TR/pointerevents3/#the-primary-pointer) is per pointer type: pen and touch can both be primary, so it is not sufficient palm rejection. **Confidence: high.**

## Recommended next steps

1. **A/B Scribble first (medium confidence mitigation, high diagnostic value).** Record iPad model, Pencil model, exact iPadOS/browser versions and current Scribble setting. Repeat the same strokes with Scribble on/off via **Settings → Apple Pencil → Scribble**, the [Apple-documented control](https://support.apple.com/guide/ipad/enter-text-with-scribble-ipad355ab2a7/ipados). Compare Chrome and Safari on the same device; agreement on this WebKit setup is not independent engine confirmation. Test latest available OS, but do not promise updating fixes it.
2. **Separate absent native input from rejected application input (high diagnostic value).** Temporarily log document/window capture-phase `pointerdown/move/up/cancel`, `gotpointercapture/lostpointercapture`, timestamps, target, `pointerId`, `pointerType`, `isPrimary`, buttons and raw pressure; correlate with overlay handler/state transitions and a screen recording. Native down present but no stroke points to targeting/state/gesture policy; no native down while rendering continues makes browser/OS arbitration more plausible, not proven. Coalesced movement samples cannot recreate a missing down.
3. **Exercise both contact orders (high-value application test).** Pencil → palm; palm → Pencil; finger tool-selection → Pencil; Pencil tool-selection → Pencil; lifted hand versus resting palm. Consider explicit pen-only drawing mode, pen takeover from an existing touch, and ignoring palm cancellation for unrelated pointer IDs. Keep intentional two-finger navigation separate rather than classifying every pair of pointers as a pinch. Tradeoff: pen-only mode reduces finger drawing/navigation and must be explicit.
4. **Verify cancellation/capture recovery (high confidence robustness).** Scope drawing-surface `touch-action: none` appropriately; ensure React Flow pan/selection does not also own draw gestures. Handle `pointercancel` and unexpected capture loss without a stuck active pointer, and allow the next pen contact to start immediately. Decide intentionally whether cancelled partial ink is discarded or retained; capture does not guarantee completion.
5. **Isolate pressure rendering (high diagnostic value, low confidence as the cause of whole missing strokes).** Compare a constant-width outline (`thinning: 0`) or raw-coordinate debug polyline against pressure-sensitive output. Preserve raw pressure in logs; distinguish a deliberate lift-off fallback from replacing every valid zero with `0.5`. Do not infer contact solely from pressure.

### Researcher handoff observations (before local reproduction)

In `prototypes/react-flow/src/Drawing.tsx:303–456`, capture and cancellation handling already exist, and coalesced events already have a fallback. The pen-active → touch guard is asymmetric: palm-first → pen enters the multiple-pointer/pinch branch. This is a concrete case for the parent's tests, **not proof of the user's failure**. `point()` replaces zero pressure with previous pressure/`0.5`; `src/ink.ts` uses real pressure for pen strokes. That policy affects width and should be distinguished from failure to receive a down. Avoid blindly adding capture, coalescing, or another geometry library as a purported fix.

The background researcher performed no source edits, dependency installs, or device tests. Its repository check was killed at typecheck (exit 137); that is not evidence of a passing check.

## Local reproduction and fix

The parent agent reproduced the palm-first failure in the actual playground using Chromium/CDP pen and touch events. `PEN_STROKES=1 node pen-smoke.mjs` failed twice before the fix: one touch down followed by one pen down/move/up produced **zero saved pen strokes**, although a surface-level fixture log confirmed the pen events reached the drawing surface. The same no-delay sequence with three consecutive pen strokes also saved zero. This separates this specific failure from absent browser input and from stroke-outline rendering.

The input handler had only protected **pen-first → palm**. **Palm-first → pen** entered its generic two-pointer branch, canceled drawing, and treated the pair as a pinch until all contacts lifted. The pen handler now explicitly cancels provisional touch/pinch state and clears those tracked touch IDs before starting the pen. Events ending or canceling a superseded palm cannot finish/cancel the active pen. This is an application-level fix, not an upgrade or change to perfect-freehand.

The focused `npm run test:pen` regression now covers 26 saved pen strokes: palm-first consecutive strokes, pen-first contact order, takeover from an active pinch, late palm cancellation/capture loss, 20 rapid taps reusing the pen ID, absence of palm ink, and reload persistence. Existing drawing and Chromium/WebKit selection regressions are also rerun separately. Tests use browser-dispatched simulated hardware events, **not a physical Apple Pencil/iPad**. Their success proves this state-machine bug is fixed; it does not establish that every missed contact on the reported device has the same cause.

Verification: the standalone playground's 23 unit tests, TypeScript/build, 26-stroke pen regression, existing component/drawing browser checks, and Chromium/WebKit selection checks passed. The full repository check did not complete within 300 seconds; it reported failures in unchanged extension/app tests before timing out. This is not a green full-repository result, and no main-app integration is performed.

If real-device misses remain, the next diagnostic is a controlled palm-lifted versus palm-resting test and Scribble-on versus Scribble-off comparison. Capture-phase device logging would then distinguish missing native events from events rejected by the app; do not add an untested fallback that invents strokes on hover or arbitrary movement.
