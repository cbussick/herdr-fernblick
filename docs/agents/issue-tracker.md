# Issue tracker: Linear

Use the Linear team `Herdr-Fernblick` for this repository's issues and specs. Resolve its team key and workspace through Linear before creating an issue or branch; do not infer either from the team name. GitHub remains the source-code host. The checked-in MCP configuration contains only the public Linear endpoint; authorize it in your client. Never commit tokens.

Before a tracker mutation, verify the available Linear tools can perform the requested operation. Read the issue description, acceptance criteria, comments, status, parent/children, and blocking relations before acting. Resolve a full identifier directly; search and disambiguate titles. Do not invent issue IDs, statuses, labels, or links. If a required operation or team workflow is missing, report it and ask for configuration rather than pretending an update succeeded.

Use the team's native Linear statuses: Needs Triage for incoming work, Backlog for accepted deferred work, Ready for actionable work, In Progress for claimed work, Done after verification and authorized integration, and Canceled or Duplicate for terminal non-delivery (record the reason or canonical issue). Verify the statuses still exist before updating issues. Use parent issues as specs and children as bounded implementation tasks; express real dependencies with native blocking relations. A parent is complete only after all required work is integrated and verified. Record decisions and verification evidence on the issue; keep the description as the canonical scope.

For concurrent agents, dispatch explicit issue identifiers rather than having multiple sessions pick the same next issue. Before editing, re-read and claim the issue (In Progress, a comment with branch and session identifier when available). A shared Linear account is not a lock: if another session has claimed it, coordinate before proceeding. Use Linear's generated branch name when available. After a human-authorized merge and successful push, add a concise comment with checks, review evidence, and commit/branch reference, then verify Done in Linear. If work is abandoned, document what remains and restore its readiness deliberately rather than automatically closing it.
